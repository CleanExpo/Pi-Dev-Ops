# Cloudroom router (router + workers + watchdog)

Humans lose track past 3-5 parallel sessions, and a session that does the work itself is
interrupted by every new message. So split the two jobs (pattern from the DeepSeek "super
agent" demo, 06/11/2026; its 15.7 vs 29.5 minute timing is the video's claim, not verified):

| Role | Is | Never |
|---|---|---|
| **Router** (this thread, the one the human talks to) | Writes tickets, dispatches, reviews against `eval.md`, sends fixes back, escalates decisions | Edits anything outside `specs/tickets/`, breaks a ticket into steps, runs the repo's build or tests, creates or deletes an `APPROVED` file |
| **Worker** (one Cloudroom child thread per ticket, own worktree and branch) | Does exactly one ticket, reports DONE or BLOCKED with evidence | Picks up other tickets, merges. Child threads: mode solo: no child threads. mode team: only its own Cloudroom child threads (`room-cli thread spawn --parent-self`), never harness subagents. |
| **Watchdog** (a Cloudroom Loop, every 10 min) | Flags stuck, silent, finished-but-unreviewed or lost workers | Fixes anything |

The router is kept out of the work by instruction, as in the video: nothing technical stops it
editing files (its own writes are tickets, the board and the commit of them). If you catch
yourself opening a source file to change it, stop and write or send a ticket instead. Reading a
worker's diff is fine (`room-cli thread show <thr> --git-diff`).

This does not replace `parallel-delegate`, `tier-orchestrator` or `persistent-subagents`.
Those use built-in harness subagents, which Cloudroom cannot see and forbids; the router uses
Cloudroom child threads so every worker is visible, steerable and survives a restart.

## Files: one writer per file

A file that a human and a script both write can always lose an edit, because an editor honours no
lock. So no file is shared (full spec: [ticket-format.md](references/ticket-format.md)):

```
specs/tickets/NNN-slug/prd.md      human (router drafts it): front matter `mode:` and `runs:`, then what, scope, not-touch
specs/tickets/NNN-slug/eval.md     human (router drafts it): how to check, edge cases, definition of done
specs/tickets/NNN-slug/APPROVED    HUMAN ONLY: its existence is the approval. Router never writes or deletes it
specs/tickets/NNN-slug/status      ROUTER ONLY, through `board.py set`: `doing worker=thr_x`
specs/tickets/NNN-slug/notes/      the worker's results and screenshots
specs/tickets/board.md             GENERATED by `board.py render`; nothing reads it back; do not edit
```

A ticket is `draft` until `APPROVED` exists, then `ready` until the router gives it a status.
Helper (stdlib Python). Shell state does not persist between tool calls, so define `b` at the top
of any Bash call that uses it (a function, so it works in zsh and bash):

```bash
b() { python3 "$HOME/.claude/skills/cloudroom-router/scripts/board.py" --tickets specs/tickets "$@"; }
b validate                      # prd front matter, eval, deps exist, no cycles, status files well formed
b next --cap 3                  # approved + ready tickets whose deps are done, within the free worker slots
b set 002 doing --worker thr_x  # writes 002's status file only, and only a move the table allows
b render                        # regenerate board.md, the view for the human to read
```

`set` validates the whole tickets folder first, then allows only: `ready`>`doing`, `doing`>`review`,
`review`>`doing`|`done`, `doing`>`doing` with a new `--worker` (hand over a lost worker),
`ready`|`doing`|`review`>`blocked`, and `blocked` back to the state it records (`was=`). A draft
cannot be moved at all. `doing` and `review` need a worker id; `doing` needs finished dependencies.
Exit 2 and `UNKNOWN` mean the tickets could not be read or written. That is never "no work".

## 1. Intake: turn a request into drafts

1. Split the human's request into features, one ticket each. Do not split a ticket into steps;
   the worker owns its own plan.
2. Ask until each ticket is unambiguous: scope, what must not be touched, decisions already made,
   how it will be checked. One batched question list, not a drip.
3. Write `prd.md` (front matter `mode:` `solo`, or `team` if the worker may fan out inside its
   own thread, and `runs:` `alongside`, or `after 001: reason` for a real dependency) and `eval.md`
   fully. No `APPROVED` file means the ticket is a draft.
4. Run `b validate` and `b render`. Tell the human the drafts are ready to read.
5. **The human approves**, by creating `specs/tickets/NNN-slug/APPROVED` (or running `b approve NNN`).
   The router never creates, edits or deletes that file and never runs `approve`. Nothing starts
   without it.

## 2. Dispatch loop

1. `b validate`, then `b next --cap 3`. Default cap is 3 local workers (the human's attention
   and the Mac's CPU are the limit). For a bigger fan-out, spawn workers with `--machine cloud`;
   say so to the human, it uses Cloud Credits.
2. **Snapshot the tickets first.** A worker's worktree is cut from a commit, and the tickets may
   exist only in this checkout. Commit them: `git add specs/tickets` then
   `git commit -m "tickets: <ids> ready"` (tickets only, never other files). Then run
   `git rev-parse HEAD` in its own call and use that literal SHA below (the release gate
   rejects `$(git ...)` substitutions).
3. For each ticket returned, fill [worker-brief.md](references/worker-brief.md) (it carries the
   absolute ticket path as a fallback) and spawn. **Local worker**, from the local snapshot commit:

```bash
room-cli thread spawn --parent-self --project "$ROOM_PROJECT_ID" --new-environment worktree \
  --base-branch <local snapshot SHA> \
  --provider <codex|cursor|claude-code> [--model <id>] --title "T<id> <slug>" \
  --prompt "$(cat /tmp/brief-<id>.md)" --json
```

   **Cloud worker** (`--machine cloud`): a cloud sandbox clones from GitHub, so it needs a PUSHED
   branch name, not a SHA. First create a branch at the snapshot, `tickets/<router thread id>`
   (a branch the router creates and owns, never any other), and push it through `pr-release-gate`.
   Then pass that name; the same command with `--machine cloud --base-branch tickets/<id>`.

4. Record it at once: `b set <id> doing --worker <new thread id>`.
5. Then stop. Do not poll. Cloudroom messages this thread when a child finishes, and the
   watchdog reports the ones that go quiet. Between those, the router answers the human.

**Provider choice.** Workers run on Codex, Cursor or Claude Sonnet, chosen per ticket (Codex for
focused code and tests, Cursor for UI and multi-file edits, Sonnet for writing and glue). The
router stays on the lead model. Omit `--model` to get the provider's catalog default rather than
naming a model that may have been retired. If a provider login is missing or expired, tell the
human which login to fix (Settings, Agents) and wait; do not switch providers silently.

## 3. Review against eval.md

When a worker reports DONE, `b set <id> review`, then check the claim yourself, from evidence:

1. Read the worker's final message (`room-cli thread output <thr>`) and `notes/`.
2. Check each line of `eval.md` against evidence the worker produced or you can read
   (`room-cli thread show <thr> --work-status --git-diff`). A worker saying "tests pass" is a
   claim, not a result; the output and the commit it ran against must be there.
3. All lines met: `b set <id> done`. Any line unmet or unproven: fix-back. `set done` is only
   reachable from `review`, so the review step cannot be skipped.
4. The worker's PR goes through `pr-release-gate`. The router opens or readies no PR and pushes only
   its own ticket-snapshot branch. Merging stays with the human.

## 4. Fix-back (same worker, same context)

Send the failing eval lines to the SAME thread; a fresh worker would lose what it learned.

```bash
room-cli thread queue create <thr> "Eval line 3 fails: <what you saw>. Fix, re-run, report DONE/BLOCKED." --json
b set <id> doing        # worker is kept; the ticket is back in the worker's hands
```

`queue create` alone is the normal send. On an IDLE thread it delivers at once, so a following
`queue send` returns HTTP 404 (observed 06/11/2026). Use `queue send <thr> <messageId>` only when
the target is busy, the message is still queued, and you must interrupt it now. Add `--hard` to
`create` to wait until the worker and its children are idle. After 3 fix-backs on the same eval line, stop looping: write what is failing into
`notes/`, `b set <id> blocked` (it records `blocked (was review)` and can only return there),
and bring it to the human as a decision.

## 5. Escalation: decisions only

Come to the human only for a decision the tickets do not already settle: scope, a product
choice, a spend, a conflict between tickets, a worker BLOCKED on something only they can
supply. Give one recommendation and ask once. Never forward a worker's raw question.
Protected actions stay human: merge, secrets, spend, production changes, force-push, deleting
branches. A worker that needs one is BLOCKED, not authorised.

## 6. The watchdog

The router hears nothing from a silent worker, so a Loop checks every 10 minutes. It flags
(one line each) `STALLED`, `WAITING_HUMAN`, `FINISHED_UNREVIEWED`, `ORPHAN`, `FAILED`
([watchdog.py](scripts/watchdog.py) header has the rules). `room-cli loop create` takes agent
flags XOR script flags, so the loop is a script loop and the script itself tells the router
(`--notify`: one `room-cli thread queue create` to this thread, only when there are flags, and not
again for the same flags within 60 minutes; no `queue send`, see section 4). Create it once per router thread, from
inside the router thread. It reads the tickets' status files, never `board.md`. This command was
accepted and run once by Cloudroom in a throwaway project on 06/11/2026 (then deleted); it is not
created for you:

```bash
room-cli loop create --project "$ROOM_PROJECT_ID" --name "router-watchdog $ROOM_THREAD_ID" \
  --cron "*/10 * * * *" --timezone UTC \
  --script-file "$HOME/.claude/skills/cloudroom-router/scripts/watchdog.py" --interpreter python3 \
  --env-json "{\"ROUTER_THREAD_ID\":\"$ROOM_THREAD_ID\",\"ROUTER_TICKETS\":\"$PWD/specs/tickets\",\"ROUTER_NOTIFY\":\"1\"}"
```

- Clean: no output, a skipped tick. Flags: printed to the run log and sent to you; the run succeeds.
- `UNKNOWN: ...` with exit 2 means `room-cli`, the tickets or the notification could not be done.
  That fails the run on purpose (an unreadable world must not look like a quiet one) and is retried
  next tick. Three in a row pause the loop; read `room-cli loop runs <loopId> --project "$ROOM_PROJECT_ID"`.
- Pause or delete it when the board is finished:
  `room-cli loop pause <loopId> --project "$ROOM_PROJECT_ID"`, or
  `room-cli loop delete <loopId> --project "$ROOM_PROJECT_ID" --yes`.
- Responding: `STALLED` and `FINISHED_UNREVIEWED`: look at the thread, then nudge it (fix-back) or
  review it. `ORPHAN`: the worker is gone; spawn a new one from the same brief, then
  `b set <id> doing --worker <new thread id>`. `WAITING_HUMAN` is the human's: tell them which
  thread is asking, in one line. `FAILED`: read `thread output`, then re-dispatch or escalate.

## Rules that stay true

- Never edit anything outside `specs/tickets/`, run builds, or open a PR from the router thread.
- Never start a worker for a ticket that is not `ready` with its dependencies `done`.
- Never mark `done` without evidence against every `eval.md` line.
- Never leave a worker running when its ticket is done or blocked: archive its thread.
- One writer per file: the router writes `status` files (through `board.py set`) and the generated
  `board.md`; the human writes `APPROVED`, `prd.md`, `eval.md`. Never write another party's file.
- Leave other threads alone; the watchdog and `thread list` filter to this router's children.

Tests: `python3 skills/cloudroom-router/tests/test_board.py`, `test_watchdog.py`, `test_docs.py`, and
`mutate_router.py` (plants faults, requires the named test to go red, and reports which tests no fault reaches).
