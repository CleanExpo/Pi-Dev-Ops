# Independent reviewer report

The independent reviewer writes this JSON itself after reviewing the exact two-dot diff and
test evidence. The implementing agent must not create or edit it.

## Check the citations before you act on the findings

```bash
python3 ~/.claude/skills/pr-release-gate/scripts/verify_reviewer_citations.py <report.json> <diff.txt>
# exit 0 = every blocking finding anchors to a real line; exit 2 = at least one does not
```

A blocking finding must quote a line that exists in the diff **under the file it names**, and
the verifier indexes the **post-image only** (`+` and context lines).

This is not defensive paranoia — it is measured. Over eight rounds on one CARSI branch
(2026-08-07) the fallback reviewer produced: a P0 that quoted a real import line but
attributed it to the **wrong file**; a P0 that quoted a `-` line and reported the branch's own
**fix** as the defect; and two findings naming patterns with **zero occurrences** in the
repository. Each is caught mechanically here, without argument. Findings that fail the check
are discarded unread, so a fabricated citation cannot block a release — and, just as
importantly, cannot be talked past either.

The verifier says nothing about whether a PASS is trustworthy. In the same eight rounds two
PASSes were returned over heads that each contained a licence-critical guard bypass. Absence
of anchored findings is not evidence of absence — for a guard or allow-list, plant the bad
string and run it rather than reading the regex.

## What a blocking finding must carry

Undocumented until 2026-08-13, when review 14 was rejected on all 16 of its findings for
using field names that every report in the estate already used. Each entry of
`blocking_findings` needs `title`, `severity`, `file`, plus one name from each pair:

```json
{
  "id": "P0-SCOPE-DIFF-MISSES-UNCOMMITTED-WORK",
  "severity": "P0",
  "title": "The scope guard inspects base..HEAD and never sees a dirty worktree",
  "file": "agents/spm/lib/scope.py",
  "line": 118,
  "quoted_line": "    args.append(f\"{base_sha}..HEAD\" if base_sha else \"HEAD\")",
  "reproduction": "…what you RAN and what it printed. `demonstration` is accepted too.",
  "suggested_fix": "…what closes it. `required_fix` is accepted too."
}
```

`quoted_line` must appear in the post-image of the diff **under the file it names** —
`verify_reviewer_citations.py` indexes `+` and context lines only, and discards findings
that fail. `id`, `line`, `where` and `why_it_matters` are conventional and unchecked.

## What PASS means

`PASS` is an **enumerable checklist**, not an absence of objections. Both clauses must hold:

1. **Every checklist item answered**, `verdict` ∈ `PASS` | `N/A`, each with `evidence` naming
   what discharged it, and every `N/A` carrying a `reason`. A `FAIL` on an item is a blocking
   finding, so it belongs in `blocking_findings` and the verdict is FAIL.
2. **Zero unresolved P0/P1 findings** — the schema-1 rule, unchanged.

The eight ids and what discharges each are owned by `REVIEW_CHECKLIST` in
`scripts/pr_release_gate.py`. `coverage` must account for **every** file in the two-dot diff:
the gate computes the changed set itself with `git diff --name-only $(git merge-base base head) head`
and rejects a ledger that omits a file or names one from another head. Declaring a file
not-reviewed is allowed with a reason; the gate prints every such file when it mints the receipt.

**Why the change (2026-08-13).** Schema 1 defined PASS as clause 2 alone, and its coverage
field — `reviewed_dimensions` — was validated against a fixed seven-string list, so it was
discharged by copying the example. On one branch, five consecutive rounds declared
byte-identical dimensions while returning 3, 2, 1, 11 and 11 findings: the low rounds were
narrower reads, and nothing in the report could say so.

P2 findings do not block (founder stopping rule, 03/08/2026): record them as documented
warnings outside `blocking_findings`, each with a tracked-ticket reference — they may not
contradict the verdict. `blocking_findings` is reserved for P0/P1. Any changed HEAD or base
invalidates the report.

**Schema 1 is still accepted for a FAIL**, so a drain loop already in flight keeps working —
its payload is its findings. Only a PASS, the verdict that releases code, requires schema 2.
