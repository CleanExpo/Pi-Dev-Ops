## Two drains, one entry, two reports

The spec asks for retry and stops there:

> - Offline capture must survive poor connectivity and retry.

Retry is named as a requirement; nothing anywhere names the mechanism that makes retry safe. Three separate races follow from that gap, all in `lib/sync-queue.ts`.

**1. There is no in-flight claim.** The drain snapshots every pending row and then holds that snapshot across a network call [VERIFIED] `lib/sync-queue.ts:25` — `const entries: Entry[] = await getAll(index, "pending");` — and the entry's status is not touched again until the fetch has already returned [VERIFIED] `lib/sync-queue.ts:38-39` — `if (!response.ok) await incrementRetry(db, entry);` / `else await removeEntry(db, entry.id);`. An entry is therefore still `"pending"` for the entire duration of its own POST. Concrete interleaving: a technician has the app open in two tabs on the same origin (or a tab plus a service worker) against the same IndexedDB. Tab A drains, POSTs entry `e`, and blocks 8s on a bad LTE link. Tab B drains 200ms later, sees `e` still `"pending"`, and POSTs it too. Two reports, one capture. No in-repo caller exists yet [VERIFIED] — `grep -rn drainQueue` over the fixture returns only the definition at `lib/sync-queue.ts:23` — which is precisely when "there will only ever be one drain" gets assumed without being written down. Prescription: claim before sending. Add a `"sending"` status and a `leaseUntil`, flip `pending → sending` in a `readwrite` transaction that re-reads the row, and skip any row already `sending` with an unexpired lease. Reclaim expired leases on drain start rather than at write time.

**2. There is no idempotency key, and nothing server-side to dedupe on.** The POST body is the raw payload [VERIFIED] `lib/sync-queue.ts:36` — `body: JSON.stringify(entry.payload),` — with no client-generated key on the wire; `entry.id` exists but is never sent. The `catch` arm cannot distinguish "the request never arrived" from "the server committed it and the response was lost" and retries both identically [VERIFIED] `lib/sync-queue.ts:40-41` — `} catch {` / `await incrementRetry(db, entry);`. The cheapest evidence settles it: the target table has no natural key at all, only a surrogate PK [VERIFIED] `supabase/migrations/001_init.sql:2` — `id uuid PRIMARY KEY DEFAULT gen_random_uuid(),` — so every duplicate arrival mints a fresh row, and `grep -rn "unique"` across `supabase/` returns nothing. Duplicates are invisible until an insurer receives the same report twice. Prescription: send `entry.id` as an `Idempotency-Key` header and persist it in a `reports.client_entry_id` column carrying `UNIQUE (tenant_id, client_entry_id)`; the handler does `INSERT ... ON CONFLICT (tenant_id, client_entry_id) DO NOTHING RETURNING id`, and an empty return is a replay that answers 200 with the original id. The key must be written in the same transaction as the report row, not after it. There is no ingest handler in the repo to check this against — the only route is `app/api/health/route.ts` [VERIFIED] `app/api/health/route.ts:1` — `export async function GET() {` — so the server half is `[INFERENCE]` and must be specified before it is written, not after.

**3. `retryCount` is a lost update.** The increment is a read-modify-write over a stale snapshot that rewrites the whole record [VERIFIED] `lib/sync-queue.ts:16-20` — `await put(db, {` … `retryCount: entry.retryCount + 1,`. Two drains that both read `retryCount: 3` both write `4`, so the budget silently doubles and `MAX_RETRY_COUNT` never binds; worse, `put` with a spread of the stale entry also clobbers any field a concurrent writer changed in between. Prescription: perform the increment inside a single `readwrite` transaction that re-reads the row by key and writes only the changed fields, and treat the claim in (1) as the thing that serialises it.

## The invariants nobody can assert today

Two properties this system needs are stated nowhere and are currently untestable. Both are assertions someone could write today.

**"One queue entry produces at most one stored report."** Nothing enforces it — see the missing unique key above. Testable form: after N concurrent drains of the same entry, `SELECT count(*) FROM reports WHERE client_entry_id = $1` is exactly 1.

**"A stored report body is never replaced by a capture taken before the version currently stored."** The payload carries no version, no `capturedAt` the server trusts, and no ETag [VERIFIED] `lib/sync-queue.ts:5-12` — the `Entry` type is `id`, `status`, `retryCount`, `nextAttemptAt`, `endpoint`, `payload` and nothing else. Two technicians on the same inspection, both offline, both syncing on reconnect: whichever POST the server happens to serve second wins, and ordering here is arrival order over two different mobile links, not capture order. That is a silent decision to accept last-writer-wins, and it may be the right one — but it must be written down, because the UI already claims otherwise. `getSyncStatus` branches on a conflict state [VERIFIED] `lib/sync-queue.ts:48-49` — `const conflictCount = await count(db, "conflict");` / `if (conflictCount > 0) return "SYNC_CONFLICT";` — while the `Entry` union admits only two statuses [VERIFIED] `lib/sync-queue.ts:6` — `status: "pending" | "failed";`. No writer can ever produce `"conflict"`, so `SYNC_CONFLICT` is dead code and the technician is shown `SYNCED` at the exact moment their colleague's readings were overwritten. Prescription: either carry a monotonic `version` (or `If-Match` on the server's ETag) and reject stale writes with 409, marking the entry `"conflict"` so the existing branch becomes live — or delete the `SYNC_CONFLICT` branch and state last-writer-wins explicitly in the spec. Shipping a status the system cannot reach is the worse of the three options.

## Backoff that does not back off

`nextAttemptAt` is computed and stored [VERIFIED] `lib/sync-queue.ts:15` — `const nextAttempt = Date.now() + RETRY_BACKOFF_MS[Math.min(entry.retryCount, 4)];` — and then never read. The selection is by status alone [VERIFIED] `lib/sync-queue.ts:24` — `const index = db.transaction("queue").objectStore("queue").index("status");` — and the loop body contains no time check before fetching [VERIFIED] `lib/sync-queue.ts:27-33` — `for (const entry of entries) {` … `const response = await fetch(entry.endpoint, {`. The `// exponential backoff` comment at `lib/sync-queue.ts:2` describes an intention, not the code.

The failure this causes, concretely: the ingest service returns 502 for 90 seconds during a deploy. Every field device with pending entries has its drain triggered by whatever wires it up — an `online` event, a visibility change, a timer — and each trigger re-POSTs the full pending set immediately, because backoff is never consulted. Every 502 also burns a retry, so after five triggers in under a minute the entries are `markFailed` and require manual recovery [VERIFIED] `lib/sync-queue.ts:28-29` — `if (entry.retryCount >= MAX_RETRY_COUNT) {` / `await markFailed(db, entry.id);`. The blast radius is the whole fleet at once and it is synchronised on the recovery moment, which is the shape that turns a 90-second deploy into a sustained outage. Prescription: filter at selection time — `entries.filter(e => (e.nextAttemptAt ?? 0) <= Date.now())` — add full jitter to each backoff step so devices do not re-converge, and do not consume a retry on 429/502/503/504; treat those as "not yet attempted" and schedule from `Retry-After` when present. The oracle that proves it: freeze the clock, fail the fetch once, drain twice in a row, assert exactly one POST and `retryCount === 1`.
