## The canonical bytes and the unique index have no oracle

The RA-7090 suite is strong where it can be: real Ed25519 keypairs, real `crypto.sign`, genuine negative cases for altered bytes, altered manifest, revoked key, binding mismatch. I am not asking for more of that. Three specific controls, however, are asserted by something that is a copy of themselves, so the edit that breaks them in production breaks no test.

**1. The canonical signed form is its own oracle.** Signing and verifying both route through one function: `lib/evidence/canonical-json.ts:10` — `export function stableStringify(value: unknown): string {` — consumed by the device seam at `lib/native/device-signing.ts:148` (`const canonicalPayload = stableStringify(manifest);`) and by the verifier at `lib/evidence/capture-manifest.ts:295` (`Buffer.from(canonicaliseCaptureManifest(manifest), "utf8"),`). Every test builds its payload the same way — `lib/evidence/__tests__/capture-manifest.test.ts:57`: `.sign(null, Buffer.from(canonicaliseCaptureManifest(manifest), "utf8"), privateKey)`. There is no frozen expected string and no frozen `(manifest, signature, publicKeyPem)` triple anywhere in the repo. [VERIFIED]

The concrete edit: change the sort comparator to `localeCompare`, or escape non-ASCII, or drop the `.filter(([, v]) => v !== undefined)`. Both sides move together, the whole suite stays green — and every signature already stored in production becomes `SIGNATURE_INVALID`. Worse, `captureReplayKey` hashes the same canonical form (`lib/evidence/capture-manifest.ts:322-327`), so the durable exactly-once key of every queued offline capture changes at the same instant and stale queues re-insert as new rows. A room name with a non-ASCII character ("Café", "Ōtāhuhu") is enough to make the two implementations disagree if any future canonicaliser ever differs. [INFERENCE — I have seen JCS-style canonicalisation drift silently break stored signatures on two prior systems; it never fails at the point of edit.]

*Prescription:* one golden-vector test holding (a) the exact expected canonical string for a fixed manifest as a literal, and (b) a hard-coded public key + base64 signature captured today, verified through `verifyCaptureManifest`. Both are constants no refactor can co-move. That test is the compile-time boundary METHOD §8 asks for, in the only form available to a wire format.

**2. The exactly-once guarantee is enforced by an index no test has executed.** `prisma/migrations/20260725000000_ra7090_evidence_capture_replay_key/migration.sql:10` — `CREATE UNIQUE INDEX "EvidenceItem_captureReplayKey_key" ON "EvidenceItem"("captureReplayKey");`. Nothing in `lib`, `app`, `scripts` or `docs/architecture` references that index name. [VERIFIED — `grep -rn "captureReplayKey_key"` returns only the migration.] What the tests exercise instead is a hand-written re-implementation: `lib/evidence/__tests__/native-capture-e2e.test.ts:125-131` — `if (data.captureReplayKey && db.evidence.some((e) => e.captureReplayKey === data.captureReplayKey)) { throw { code: "P2002" }; }`. Delete the `CREATE UNIQUE INDEX` line and every test still passes. The migration comment's own promise — "a queued offline capture can replay later than that, so exactly-once is enforced by a unique replay key persisted on the evidence row itself" — is exactly the sentence with no oracle behind it. [VERIFIED]

**3. The FK's custody guarantee is asserted by regex over the SQL text.** `lib/__tests__/ra7090-original-asset-linkage-contract.test.ts:78-80` asserts `activeSql(migration)` matches `/ALTER TABLE "EvidenceItem" ADD CONSTRAINT ... ON DELETE RESTRICT/`. That proves the string was typed. It cannot distinguish an applied constraint from an unapplied one, and it is written in the same commit by the same hand as the SQL it reads, so it is a transcription check, not a behaviour check. [VERIFIED]

*Prescription for 2 and 3, and this is the cheap part:* PR CI already provisions Postgres and applies migrations — `.github/workflows/pr-checks.yml:210` "Apply migrations for DB-gated tests" runs before `pnpm exec vitest run` at :217. [VERIFIED] So one DB-gated suite (the repo's existing `describe.skipIf(!process.env.DATABASE_URL)` pattern, already guarded from silent-skip by `scripts/ci/check-test-parity.mjs`) can do all three positive controls in under fifty lines: insert two `EvidenceItem` rows with the same `captureReplayKey` and assert P2002; delete an `InspectionPhoto` with a dependent `EvidenceItem` and assert the FK error code; insert two rows with `captureReplayKey: null` and assert both succeed (the NULL-exemption the migration relies on). Until one of those has been observed failing when the constraint is removed, "exactly-once" and "the database itself must refuse to delete it" are claims, not results.

One line where the method beat my instinct: my reflex is to demand mutation testing over the whole suite (there is none — no `stryker`, no coverage gate in `package.json` or `pr-checks.yml` [VERIFIED]). METHOD §1 and §13 say prescribe the boring version first: run the three named mutations by hand, once, and record the result. A suite-wide mutation run is a cost this change has not earned.

## Swift wire format drifts with nothing to catch it

The bytes that actually reach the verifier in the field are produced by 541 lines of Swift under `ios/App/App/Plugins/`. Their only oracle is a hand-transcribed replica inside a Node test. `lib/native/__tests__/native-plugin-interop.test.ts:5-6` says so plainly — "The Swift plugins cannot execute in this Node test runner, so these tests pin the exact BYTE FORMATS the Swift sources are written to emit" — and :42-48 re-implements `DeviceSigningKeys.swift`'s PEM construction in TypeScript, while :126-132 hard-codes a fixture string claimed to be what `RoomPlanSerialization.swift` emits. [VERIFIED]

Nothing links the copy to the original. There is no reference to any `.swift` file in `scripts/` or in any workflow. [VERIFIED — `grep -rln "\.swift" scripts/ .github/workflows/` returns nothing beyond the release job.] And the Swift is not compiled on a pull request at all: `.github/workflows/ios-release.yml:3-7` triggers only on `push: tags: - "v[0-9]+.[0-9]+.[0-9]+"` and `workflow_dispatch`. [VERIFIED] There is no iOS test target in the project — `ios/App/App.xcodeproj/project.pbxproj` contains no `XCTest` reference. [VERIFIED]

The failure that will actually happen: someone changes `String(format: "%.4f", ...)` to `%.6f` in `RoomPlanSerialization.swift:31`, or reorders the emitted keys, or adds a field. Every check in PR CI is green, including the interop test that claims to pin that format. The next TestFlight build ships, a technician scans a room, and the server recomputes SHA-256 over bytes that no longer match the signed manifest — `ORIGINAL_BYTES_HASH_MISMATCH`, 422, on every native capture from every device. Nobody learns this from CI; they learn it from a field technician whose captures all fall back to UNSIGNED. The same holds for `DeviceSigningKeys.swift`'s SPKI construction: a wrong DER prefix produces a PEM the server rejects at enrolment, on hardware only. [INFERENCE — the mechanism is a duplicated constant across a language boundary with no shared source; I have watched it bite on protobuf-adjacent hand-rolled wire formats twice.]

*Prescription, cheapest first:* add a macOS job to `pr-checks.yml` that runs `swift build` (or `xcodebuild -target App`) on any PR touching `ios/**` — it at least catches a Swift file that no longer compiles, which today nothing catches. Then make the fixture generated rather than transcribed: a tiny `swift run` fixture-emitter that prints `RoomPlanSerialization.capturedRoomJson(...)` and `spkiPem(...)` for fixed inputs to a checked-in `ios/fixtures/*.json`, with CI failing when the emitted bytes differ from the committed file. The TS interop test then reads that file instead of a literal, and the copy stops being a copy. If a macOS runner is judged too expensive for every PR, gate it on the `ios/**` path filter — the honest alternative is to record in the PR that the Swift wire format has no oracle and that any iOS release is the first execution of that code, which is the current state and is what makes this blocking.

**Credit where the spec already decided this.** `spec.md:391` requires "use a positive control to prove the new test detects the original defect", and `spec.md:392` says "'No errors observed' is not evidence." The rule exists; this change did not apply it to the three controls above. That is why the state is `PRESCRIBED` rather than a complaint about absent thinking — the thinking is in the spec, the artefact is missing from the branch.
