## Offline queue blast radius

The spec gate is `> Offline capture must survive poor connectivity and retry.` The queue as written converts poor connectivity into silent, permanent loss of a technician's captured readings, and does it within seconds rather than over the intended 48 seconds of backoff.

**1. The backoff is computed, stored, and never read.** `incrementRetry` writes the next attempt time [VERIFIED] `lib/sync-queue.ts:19` — `nextAttemptAt: nextAttempt,`. Nothing ever reads it back: the drain selects purely on status [VERIFIED] `lib/sync-queue.ts:24` — `const index = db.transaction("queue").objectStore("queue").index("status");` and the only guard in the loop is the counter [VERIFIED] `lib/sync-queue.ts:28` — `if (entry.retryCount >= MAX_RETRY_COUNT) {`. A repo-wide grep for `nextAttemptAt` returns exactly the two lines that write it and zero that compare it to `Date.now()`. Concrete scenario: the report endpoint returns 502 for 30 seconds during a deploy. A technician's entry is retried on every drain tick with no delay at all, burns `retryCount` 0→5 in the time of five sequential fetches, and is moved to `failed` [VERIFIED] `lib/sync-queue.ts:29` — `await markFailed(db, entry.id);` before the deploy has finished. The transient outage the backoff exists to absorb is exactly the case it does not absorb. The drain cadence itself is not in this fixture (`grep -rn drainQueue` finds no caller), so the exact amplification factor is [INFERENCE]; the field being write-only is [VERIFIED] and is true at any cadence.

**2. `failed` is invisible to the status the technician sees.** `getSyncStatus` counts two buckets [VERIFIED] `lib/sync-queue.ts:48` — `const conflictCount = await count(db, "conflict");` — and `"conflict"` is not even a member of the declared union [VERIFIED] `lib/sync-queue.ts:6` — `status: "pending" | "failed";`, so that branch is permanently dead. `"failed"` is counted nowhere. The fall-through is [VERIFIED] `lib/sync-queue.ts:51` — `return "SYNCED";`. So the moment the last entry is marked failed, pendingCount hits zero and the app tells the technician **SYNCED** while their readings are stranded in IndexedDB on a device that will be wiped or reassigned. This is the fail-open-into-wrongness pattern: the failure state is not merely unalerted, it is actively rendered as success. Nobody notices until an insurer asks for a report that was never captured — weeks.

**3. The outbound fetch has no timeout, and the loop is serial.** [VERIFIED] `lib/sync-queue.ts:33` — `const response = await fetch(entry.endpoint, {` — with no `signal`. The same repo demonstrably knows how to bound a client: [VERIFIED] `lib/notify.ts:15` — `signal: AbortSignal.timeout(10_000),`. Because the drain awaits each entry in order [VERIFIED] `lib/sync-queue.ts:27` — `for (const entry of entries) {` — one request that hangs against a captive-portal or half-open TCP connection (the normal case for a technician driving out of a basement, which is the environment this queue exists for) blocks every subsequent entry indefinitely. Head-of-line blocking on a queue whose whole purpose is degraded connectivity. [INFERENCE] on the hang duration — browsers eventually fail the socket, but on the order of minutes, and a service-worker drain tick will not survive that.

**4. Retries are not idempotent and not jittered.** The request is a bare POST with no idempotency key [VERIFIED] `lib/sync-queue.ts:34` — `method: "POST",`, and the `catch` cannot distinguish "server never received it" from "server committed and the response was lost" [VERIFIED] `lib/sync-queue.ts:40` — `} catch {`. Both paths call `incrementRetry` and re-POST, so a response lost after commit produces a duplicate report. Separately the delay table is a fixed constant [VERIFIED] `lib/sync-queue.ts:2` — `const RETRY_BACKOFF_MS = [1000, 2000, 5000, 10000, 30000]; // exponential backoff` — with no randomisation, so once (3) is fixed, an entire crew reconnecting after a site-wide dead zone retries on the identical 1s/2s/5s schedule and arrives as a synchronised herd.

**Prescription** (grounded in the code above, not in a spec sentence — the author may overturn it):
- Filter the drain on `nextAttemptAt === null || nextAttemptAt <= Date.now()`, or delete the field and admit there is no backoff.
- Add `AbortSignal.timeout(...)` to the queue fetch, matching the bound already used in `notify.ts`; make the drain tolerate one entry timing out without stalling the rest.
- Send a client-generated idempotency key (the entry `id` is already a stable uuid) and have the server dedupe on it, so a lost response is safe to retry.
- Jitter the delay (`base * (0.5 + Math.random())`).
- Count `"failed"` in `getSyncStatus` and return a distinct state; `SYNCED` must be reachable only when nothing is pending **and** nothing is failed. This is the single change with the largest blast-radius reduction and is why this category is `blocking`.

## Health and watchdog report success unconditionally

Both of the things that would tell an operator the system is broken report healthy by construction.

`runWatchdog` sets its own success flag from control flow, not from a result [VERIFIED] `lib/notify.ts:28` — `alerted = true;` — placed immediately after a call to a function that is documented as unable to fail [VERIFIED] `lib/notify.ts:2` — `* Fire-and-forget: reports errors loudly but never throws, so callers do not fail.` `sendEmail` returns `void` on every path, including the one where the credential is missing [VERIFIED] `lib/notify.ts:8` — `return;` — and the one where the provider 5xxs [VERIFIED] `lib/notify.ts:17` — `if (!res.ok) console.error("[notify] non-2xx", res.status);`. Concrete scenario: `RESEND_API_KEY` is not set in the production environment (a plausible single-variable omission, and nothing in this repo asserts its presence). Every unhealthy job produces `{ healthy: false, alerted: true }` — a caller, dashboard, or escalation rule reading `alerted` concludes a human was told. Nobody was told; a line went to stdout. And if `ALERT_EMAIL` is unset the guard [VERIFIED] `lib/notify.ts:26` — `if (to) {` — skips silently, so the absence of an alert channel is itself unalerted.

The HTTP health surface has the same shape: it returns a literal [VERIFIED] `app/api/health/route.ts:3` — `status: "ok",` — computed from nothing. It does not probe the database, does not report queue depth, and does not report failed-entry count. So an uptime monitor and a load balancer both read 200/ok while the deployed database is still on the pre-003 permissive policy, while technician queues are stranded, and while no email can be sent.

The gap this leaves is absence-detection, which is the class of outage nothing here can see: a drain worker that stops running entirely produces zero errors, zero non-2xx logs, and a perfectly green health endpoint.

**Prescription:** derive `alerted` from a value returned by `sendEmail` (make it return `boolean` or throw and let the watchdog catch), treat a missing `ALERT_EMAIL` or `RESEND_API_KEY` as a startup failure rather than a runtime no-op, and make `/api/health` report at least one observed fact — a DB round-trip and the count of entries in `failed` — so that "ok" is a measurement rather than a string literal. Add one heartbeat with a staleness alarm so a drain that dies entirely is detectable by absence.

**Disagreement / overlap:** `eng-observability` never sits out and will very likely answer `observability` too. I am not overwriting it — record both. If our prescriptions differ, mine is scoped narrowly to the two success signals that are fabricated rather than measured, and I would not withdraw the `blocking` flag on that basis: a fabricated `alerted: true` is worse than no alerting at all, because it retires the question.
