# Code Review Skill

Conduct a thorough code review for quality, security, and maintainability with severity-rated feedback.

## When to Use

This skill activates when:
- User requests "review this code", "code review"
- Before merging a pull request
- After implementing a major feature
- User wants quality assessment

## What It Does

## GPT-5.4 Guidance Alignment

- Default to concise, evidence-dense progress and completion reporting unless the user or risk level requires more detail.
- Treat newer user task updates as local overrides for the active workflow branch while preserving earlier non-conflicting constraints.
- If correctness depends on additional inspection, retrieval, execution, or verification, keep using the relevant tools until the review is grounded.
- Continue through clear, low-risk, reversible next steps automatically; ask only when the next step is materially branching, destructive, or preference-dependent.

Delegates to the `code-reviewer` agent (THOROUGH tier) for deep analysis:

1. **Identify Changes**
   - Run `git diff` to find changed files
   - Determine scope of review (specific files or entire PR)

2. **Review Categories**
   - **Security** - Hardcoded secrets, injection risks, XSS, CSRF
   - **Code Quality** - Function size, complexity, nesting depth
   - **Performance** - Algorithm efficiency, N+1 queries, caching
   - **Best Practices** - Naming, documentation, error handling
   - **Maintainability** - Duplication, coupling, testability

3. **Severity Rating**
   - **CRITICAL** - Security vulnerability (must fix before merge)
   - **HIGH** - Bug or major code smell (should fix before merge)
   - **MEDIUM** - Minor issue (fix when possible)
   - **LOW** - Style/suggestion (consider fixing)

4. **Specific Recommendations**
   - File:line locations for each issue
   - Concrete fix suggestions
   - Code examples where applicable

## Agent Delegation

```
delegate(

  tier="THOROUGH",
  prompt="CODE REVIEW TASK

Review code changes for quality, security, and maintainability.

- Best practices (naming, documentation, error handling)
- Maintainability (coupling, testability)

Output: Code review report with:
- Files reviewed count
- Issues by severity (CRITICAL, HIGH, MEDIUM, LOW)
- Specific file:line locations
- Fix recommendations
- Approval recommendation (APPROVE / REQUEST CHANGES / COMMENT)"
)
```

## External Model Consultation (Preferred)

### Protocol
1. **Form your OWN review FIRST** - Complete the review independently
2. **Consult for validation** - Cross-check findings with Codex
3. **Critically evaluate** - Never blindly adopt external findings

### When to Consult
- Security-sensitive code changes
- Complex architectural patterns
- Unfamiliar codebases or languages

### When to Skip
- Simple refactoring
- Well-understood patterns
- Time-critical reviews
- Small, isolated changes

## Review Checklist

The code-reviewer agent checks:

### Security
- [ ] No hardcoded secrets (API keys, passwords, tokens)
- [ ] All user inputs sanitized
- [ ] SQL/NoSQL injection prevention
- [ ] XSS prevention (escaped outputs)
- [ ] CSRF protection on state-changing operations
- [ ] Authentication/authorization properly enforced

### Code Quality
- [ ] Functions < 50 lines (guideline)
- [ ] Cyclomatic complexity < 10
- [ ] No deeply nested code (> 4 levels)
- [ ] No duplicate logic (DRY principle)
- [ ] Clear, descriptive naming

### Performance
- [ ] No N+1 query patterns
- [ ] Appropriate caching where applicable
- [ ] Efficient algorithms (avoid O(nÂ²) when O(n) possible)
- [ ] No unnecessary re-renders (React/Vue)

### Best Practices
- [ ] Error handling present and appropriate
- [ ] Logging at appropriate levels
- [ ] Documentation for public APIs
- [ ] Tests for critical paths
- [ ] No commented-out code

## Approval Criteria

**APPROVE** - No CRITICAL or HIGH issues, minor improvements only
**REQUEST CHANGES** - CRITICAL or HIGH issues present
**COMMENT** - Only LOW/MEDIUM issues, no blocking concerns


## Scenario Examples

**Good:** The user says `continue` after the workflow already has a clear next step. Continue the current branch of work instead of restarting or re-asking the same question.

**Good:** The user changes only the output shape or downstream delivery step (for example `make a PR`). Preserve earlier non-conflicting workflow constraints and apply the update locally.

**Bad:** The user says `continue`, and the workflow restarts discovery or stops before the missing verification/evidence is gathered.

- **Learn from reviews** - Use feedback to improve coding practices

     3	// Both app/api/auth/login/route.ts (which signs cookies) and proxy.ts (which
     4	// validates them) MUST resolve the secret the same way, otherwise login
     5	// succeeds but every protected page redirects back to login. Before this
     6	// module the two callers had subtly different logic — login fell back to
     7	// "dev" in non-production while proxy returned an empty string, causing a
     8	// redirect loop in any local-dev session without a .env.local.
     9	//
    10	// This module is the only place that decision lives. Edit here, both
    11	// callers stay in sync.
    12	
    13	interface ResolvedSecret {
    14	  /** The secret used to sign + verify session HMACs. */
    15	  value: string;
    16	  /** True when running with the "dev" fallback. */
    17	  dev: boolean;
    18	  /** Reason the real env var was unusable (logged once at startup). */
    19	  reason: "ok" | "unset" | "unresolved-1password";
    20	}
    21	
    22	/**
    23	 * Resolve the dashboard auth secret.
    24	 *
    25	 * Priority:
    26	 *   1. DASHBOARD_PASSWORD (preferred — human-facing login secret)
    27	 *   2. PI_CEO_PASSWORD (fallback — same secret reused for backend auth)
    28	 *   3. Dev fallback "dev" — ONLY in non-production builds
    29	 *
    30	 * Vercel-specific quirks handled:
    31	 *   - .trim() to drop trailing newlines that the Vercel CLI sometimes adds
    32	 *   - "op://..." prefix detection — unresolved 1Password CLI references
    33	 *     that the Vercel CLI creates by default when you `vercel env pull`.
    34	 *     These are TREATED AS IF UNSET and trigger the dev fallback.
    35	 */
    36	export function resolvePassword(): ResolvedSecret {
    37	  const raw = (process.env.DASHBOARD_PASSWORD || process.env.PI_CEO_PASSWORD || "").trim();
    38	
    39	  if (raw && !raw.startsWith("op://")) {
    40	    return { value: raw, dev: false, reason: "ok" };
    41	  }
    42	
    43	  const reason: ResolvedSecret["reason"] = raw.startsWith("op://")
    44	    ? "unresolved-1password"
    45	    : "unset";
    46	
    47	  if (process.env.NODE_ENV !== "production") {
    48	    return { value: "dev", dev: true, reason };
    49	  }
    50	
    51	  // Production with no usable secret — return empty so callers can refuse
    52	  // to authenticate and surface the misconfiguration instead of silently
    53	  // accepting the dev fallback.
    54	  return { value: "", dev: false, reason };
    55	}

    58	export function authSecret(): string {
    59	  return resolvePassword().value;

    62	/**
    63	 * Verify a `pi_session` token: `<issuedAtSeconds>.<hexHmacSha256(issuedAt)>`.
    64	 *
    65	 * This lives here, next to `resolvePassword`, for the reason this module exists at all:
    66	 * two callers once resolved the secret differently and login succeeded while every
    67	 * protected page bounced. Verification is now about to have two callers too — `proxy.ts`
    68	 * and `/api/kill-switch` — so it is defined once rather than copied and left to drift.
    69	 *
    70	 * Returns false for anything malformed, expired, or signed with a different secret. It
    71	 * never throws, so a caller cannot accidentally treat a thrown error as "authenticated".
    72	 */
    73	export async function verifySessionToken(
    74	  token: string,
    75	  ttlSeconds = 86_400,
    76	): Promise<boolean> {
    77	  const secret = resolvePassword().value;
    78	  if (!secret || !token) return false;
    79	
    80	  const dot = token.indexOf(".");
    81	  if (dot === -1) return false;
    82	
    83	  const issuedAtStr = token.slice(0, dot);
    84	  const sig = token.slice(dot + 1);
    85	  const issuedAt = parseInt(issuedAtStr, 10);
    86	  if (Number.isNaN(issuedAt)) return false;
    87	
    88	  const age = Math.floor(Date.now() / 1000) - issuedAt;
    89	  if (age < 0 || age > ttlSeconds) return false;
    90	
    91	  try {
    92	    const enc = new TextEncoder();
    93	    const key = await crypto.subtle.importKey(
    94	      "raw",
    95	      enc.encode(secret),
    96	      { name: "HMAC", hash: "SHA-256" },
    97	      false,
    98	      ["sign"],
    99	    );
   100	    const expected = await crypto.subtle.sign("HMAC", key, enc.encode(issuedAtStr));
   101	    const expectedHex = Array.from(new Uint8Array(expected))
   102	      .map((b) => b.toString(16).padStart(2, "0"))
   103	      .join("");
   104	    return expectedHex === sig;
   105	  } catch {
   106	    return false;
   107	  }
   108	}

   122	export async function proxy(req: NextRequest): Promise<NextResponse | Response> {
   123	  const { pathname } = req.nextUrl;
   124	
   125	  // ── Auth ───────────────────────────────────────────────────────────────────
   126	  const isProtectedPage = PROTECTED_PAGE_PREFIXES.some((p) => pathname.startsWith(p));
   127	  const isPublicApi = PUBLIC_API_PREFIXES.some((p) => pathname.startsWith(p));
   128	  const isProtectedApi = !isPublicApi && PROTECTED_API_PREFIXES.some((p) => pathname.startsWith(p));
   129	
   130	  if (isProtectedPage || isProtectedApi) {
   131	    const token = req.cookies.get(COOKIE_NAME)?.value ?? "";
   132	    const valid = await verifySession(token);
   133	
   134	    if (!valid) {
   135	      if (isProtectedApi) {
   136	        return Response.json({ error: "Unauthorised" }, { status: 401 });
   137	      }
   138	      const loginUrl = new URL(LOGIN_PATH, req.url);
   139	      loginUrl.searchParams.set("redirect", pathname);
   140	      return NextResponse.redirect(loginUrl);
   141	    }
   142	  }
   143	
   144	  // ── CSP nonce ──────────────────────────────────────────────────────────────
   145	  const nonce = btoa(crypto.randomUUID()); // btoa works in Edge runtime; Buffer does not
   146	  const csp = buildCsp(nonce);
   147	
   148	  const requestHeaders = new Headers(req.headers);
   149	  requestHeaders.set("x-nonce", nonce);
   150	
   151	  const response = NextResponse.next({ request: { headers: requestHeaders } });
   152	  response.headers.set("Content-Security-Policy", csp);
   153	
   154	  return response;
   155	}
